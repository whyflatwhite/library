# Правила внесения изменений

Эти правила обязательны для всех участников команды.
Любое изменение - потенциально ошибочное, пока не прошло проверки ниже.

## Путь изменения

```
задача -> изменение кода -> локальные проверки -> Git -> CI -> образ -> CD -> проверка релиза -> наблюдение
```

1. **Задача** - заводится в трекере задач репозитория (GitHub Issues) с четким описанием:
   что делаем и зачем, критерии готовности (Definition of Done).
2. **Ветка** - от `main` создается ветка вида `feature/<issue-номер>-краткое-описание`
   (например `feature/12-add-copy-return`).
3. **Коммиты** - несколько осмысленных коммитов (не один "wip"), сообщение в формате
   `тип: краткое описание` (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
4. **Локальные проверки перед пушем** - обязательно:
   - `make quality` - форматирование (black, isort) и статический анализ (flake8, mypy);
   - `make test` - модульные тесты;
   - `make container-check` - образ собирается и `/health` отвечает.
   Все вместе - `make verify`.
5. **Pull Request** в `main`:
   - описание: что изменено и зачем, ссылка на задачу;
   - обязательный ревью хотя бы от одного другого участника команды;
   - CI (GitHub Actions) должен пройти зеленым: quality, tests, build image, migration-check;
   - если PR затрагивает критические файлы приемки (`Makefile`, `.github/workflows/*`,
     `docker-compose.yml`, `Dockerfile`, `migrations/*`, `docs/CONTRIBUTING.md`) - это
     явно указывается в описании PR, и ревьюер обязан отдельно проверить эти файлы.
6. **Слияние** - только после зеленого CI и апрува ревьюера. Merge в `main`.
7. **CI** - на каждый PR и на каждый push в `main` автоматически прогоняются:
   линтеры, тесты, сборка Docker-образа, применение миграций к чистой БД.
8. **Образ / CD** - из `main` собирается Docker-образ (тег = короткий SHA коммита или
   версия), разворачивается через `docker compose up`.
9. **Проверка релиза** - после разворачивания вручную или скриптом проверяется `/health`
   и один-два ключевых сценария (создание книги, выдача экземпляра).
10. **Наблюдение** - логи приложения (`logging`, уровень задается `LOG_LEVEL`) проверяются
    на ошибки после раскатки; при проблеме - откат на предыдущий образ/тег.

## Что запрещено делать ради прохождения проверки

- Удалять или закомментировать тесты.
- Отключать анализаторы (flake8/mypy/black) точечно без обоснования и обсуждения в PR.
- Снижать пороги качества (например, покрытие тестами) без согласования с командой.
- Мержить в `main`, минуя CI или ревью, даже "временно".
- Коммитить `.env`, реальные пароли, дампы БД с персональными данными.

## Версионирование

- Первая рабочая версия помечается тегом `v0.1.0` после того, как:
  минимальный HTTP API + БД работают, есть health-check, тесты зеленые,
  README и .env.example на месте.
- Дальнейшие теги - по семантическому версионированию (`vMAJOR.MINOR.PATCH`).

## Обязательные команды (см. также Makefile)

| Команда              | Назначение                                   |
|----------------------|-----------------------------------------------|
| `make setup`         | Первоначальная настройка (venv + зависимости) |
| `make run`           | Локальный запуск API                          |
| `make test`          | Автотесты                                     |
| `make quality`       | Форматирование + статический анализ           |
| `make migrate`       | Применение миграций Alembic                   |
| `make backup`        | Резервная копия БД                            |
| `make restore`       | Восстановление БД из резервной копии          |
| `make verify`        | Полный набор локальных проверок               |
| `make up` / `down`   | Поднять / остановить контейнерное окружение   |
| `make container-check`| Проверка, что образ собирается и API жив     |
