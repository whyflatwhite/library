# Правила внесения изменений

Эти правила обязательны для всех участников команды.
Любое изменение - потенциально ошибочное, пока не прошло проверки ниже.

## Путь изменения

```
задача -> изменение кода -> локальные проверки -> Git -> CI -> образ -> CD -> проверка релиза -> наблюдение
```

1. **Задача** - заводится в трекере задач репозитория (GitHub Issues) с четким описанием:
   что делаем и зачем, критерии готовности (Definition of Done).
2. **Ветка** - от `main` создается ветка вида `feature/<issue-номер>-краткое-описание`
   (например `feature/12-add-copy-return`).
3. **Коммиты** - несколько осмысленных коммитов (не один "wip"), сообщение в формате
   `тип: краткое описание` (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
4. **Локальные проверки перед пушем** - обязательно:
   - `make quality` - форматирование (black, isort), статический анализ (flake8, mypy)
     и анализ безопасности кода SAST (bandit);
   - `make test` - unit- и интеграционные тесты, миграции, резервное копирование;
     покрытие не ниже порога `fail_under` в `pyproject.toml`; отчеты в `reports/`;
   - `make container-check` - автоматическая проверка контейнерного окружения (Linux + Docker);
     обязательна, если менялись `Dockerfile`, `.dockerignore`, `docker-compose.yml` или
     `scripts/container_*.sh`; результат указывается в описании PR.
   Код проверяет `make verify`, контейнерное окружение - `make container-check`.
5. **Pull Request** в `main`:
   - описание: что изменено и зачем, ссылка на задачу;
   - обязательный ревью хотя бы от одного другого участника команды;
   - CI (GitHub Actions) должен пройти зеленым: quality, tests, build image, migration-check;
   - если PR затрагивает критические файлы приемки (`Makefile`, `.github/workflows/*`,
     `docker-compose.yml`, `Dockerfile`, `migrations/*`, `pyproject.toml`, `docs/CONTRIBUTING.md`) - это
     явно указывается в описании PR, и ревьюер обязан отдельно проверить эти файлы.
6. **Слияние** - только после зеленого CI и апрува ревьюера. Merge в `main`.
7. **CI** - на каждый PR и на каждый push в `main` автоматически прогоняются:
   линтеры, тесты, сборка Docker-образа, применение миграций к чистой БД.
8. **Образ / CD** - из `main` собирается Docker-образ (тег = короткий SHA коммита или
   версия), разворачивается через `docker compose up`.
9. **Проверка релиза** - после разворачивания вручную или скриптом проверяется `/health`
   и один-два ключевых сценария (создание книги, выдача экземпляра).
10. **Наблюдение** - логи приложения (`logging`, уровень задается `LOG_LEVEL`) проверяются
    на ошибки после раскатки; при проблеме - откат на предыдущий образ/тег.

## Что запрещено делать ради прохождения проверки

- Удалять, закомментировать или пропускать тесты (`skip`, `skipif`, `xfail`).
- Отключать анализаторы (flake8/mypy/black/bandit) и добавлять исключения (`noqa`, `type: ignore`,
  `nosec`) без письменного обоснования рядом с исключением и обсуждения в PR.
- Снижать пороги качества (например, `fail_under` в `pyproject.toml`) и ослаблять CI.
  Пороги можно только повышать.
- Мержить в `main`, минуя CI или ревью, даже "временно".
- Коммитить `.env`, реальные пароли, дампы БД с персональными данными.

## Версионирование

- Первая рабочая версия помечается тегом `v0.1.0` после того, как:
  минимальный HTTP API + БД работают, есть health-check, тесты зеленые,
  README и .env.example на месте.
- Дальнейшие теги - по семантическому версионированию (`vMAJOR.MINOR.PATCH`).

## Обязательные команды (см. также Makefile)

| Команда              | Назначение                                   |
|----------------------|-----------------------------------------------|
| `make setup`         | Первоначальная настройка (venv + зависимости) |
| `make run`           | Локальный запуск API                          |
| `make test`          | Автотесты                                     |
| `make quality`       | Форматирование + статический анализ + SAST    |
| `make migrate`       | Применение миграций Alembic                   |
| `make backup`        | Резервная копия БД                            |
| `make restore`       | Восстановление БД из резервной копии          |
| `make verify`        | `make quality` + `make test`                  |
| `make up` / `down`   | Поднять / остановить контейнерное окружение   |
| `make container-check`| Полная проверка контейнерного окружения      |
| `make container-migrate` | Миграции в контейнере                     |
| `make container-backup`  | Резервная копия БД из контейнера          |
| `make container-restore` | Восстановление (`FILE=...` - из файла)    |

## Миграции, резервное копирование и тесты

- Схема БД меняется только миграцией Alembic: новая миграция - `alembic revision --autogenerate -m "..."`,
  применение - `make migrate`. Цепочка: `0001` (схема), `0002` (users), `0003` (срок возврата `loans.due_at`).
- `make backup` создает копию в `backups/` (PostgreSQL - `pg_dump`, SQLite - копия файла),
  `make restore` восстанавливает из самой свежей копии или из `FILE=backups/<файл>`.
  Выполнять под пользователем, владеющим таблицами. Пароль берется из `DATABASE_URL` и передается
  утилитам через `PGPASSWORD`.
- Тесты идут на отдельной БД в памяти: `tests/conftest.py` до запуска приложения задает
  `APP_ENV=test` и `DATABASE_URL=sqlite:///:memory:`, у каждого теста своя пустая БД.
- Покрытие функций ТЗ тестами (не менее 40%): создание сущностей и книг, выдача и возврат,
  правило «нельзя выдать повторно», срок возврата, регистрация и вход, health-check -
  7 из 8 основных функций (не покрыты только отчеты).

## Контейнерное окружение

- Образ собирается из `python:3.12.7-slim-bookworm` (точная версия), зависимости закреплены в
  `requirements.txt`, в образ попадает только код приложения (`.dockerignore`).
- Приложение работает от пользователя `app` (uid 10001). Настройки и пароли передаются переменными
  окружения из файла `.env` (в git и в образ он не попадает), шаблон - `.env.example`.
- Команда запуска `uvicorn` записана в exec-форме, поэтому процесс получает SIGTERM и завершается
  корректно; `stop_grace_period` - 15 секунд.
- Compose: сети `backend`, именованный volume `pgdata`, healthcheck у `db` и `api`, `api` стартует
  после здоровой БД (`depends_on: service_healthy`). Порт БД наружу не публикуется.
- Лимиты ресурсов: `api` - 256 МБ и 0.5 CPU (приложение занимает около 100 МБ), `db` - 512 МБ и
  1 CPU (небольшая БД). Лимиты защищают ВМ от исчерпания памяти одним контейнером.
- `make container-check` на отдельном проекте Compose `library_check` (порт 18080, данные рабочих
  контейнеров не затрагиваются) проверяет: правила ниже, сборку и запуск, миграции, пользователя
  процесса, закрытый порт БД, healthcheck и лимиты, сохранность данных после пересоздания и обновления
  образа, корректное завершение по SIGTERM, восстановление копии в новый volume.
  Статические правила дополнительно проверяет `tests/test_container_rules.py` в `make verify`.

### Что запрещено в контейнерном окружении

- Использовать тег `latest` (в `FROM` и в `image`).
- Запускать приложение от root.
- Помещать секреты (пароли, токены) в образ, `Dockerfile` и `docker-compose.yml`.
- Отключать или удалять healthcheck.
- Публиковать порты, кроме порта приложения (в частности, порт БД).
- Менять контейнерное окружение без успешного `make container-check`.
